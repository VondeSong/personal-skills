# Git / GitHub 工作流

将流程复用于不同项目，保留每个项目的配置、授权和技术栈。默认中文提交与中文发布说明；项目另有明确约定时按其约定执行。

## 入口与授权

先读当前项目适用的 `AGENTS.md`，再决定本次需要哪些阶段：

| 请求或项目状态 | 执行范围 |
| --- | --- |
| 初始化 Git、建立/关联 GitHub 仓库、接入版本管理 | 阅读 [初始化流程](references/initialize.md)；新建仓库包含开发总看板接入 |
| 补齐看板模块/视图或 README 开发协作入口 | 阅读 [看板与协作入口](references/projects.md)，按项目证据适配并沿用已有配置 |
| 明确交办修复某个 Issue、实现路线图功能或里程碑 | 阅读 [任务执行流程](references/issue-workflow.md)，完成开发至进度回读 |
| 明确要求保存/同步，或项目已授权检查后自动保存 | 执行下方“检查后保存与同步” |
| 用户明确要求发布，或用户预先指定的发布条件实际满足 | 阅读 [Release 流程](references/release.md) |
| 只读检查、调研、解释、仅生成提交文案 | 保持只读，不顺带初始化、提交、推送或发布 |

- 技能描述操作方法，不能代替用户或项目授权。已有授权直接执行，不重复询问；缺少关键目标或写入授权时，只询问缺失部分，并继续独立的只读检查。
- 用户已选择本技能的默认范围：新建 GitHub 仓库时创建或关联开发总看板，依据项目实际功能配置模块和视图，并在 README 添加开发协作入口；明确交办具体 Issue 或路线图任务时，完成该范围内的开发、检查、中文提交同步及 Issue/看板进度维护。执行前将适用范围与项目参数记录或核对在该项目 `AGENTS.md`，已有明确约定优先沿用，不重复询问。
- 上述范围不授权自行挑选其他待办、遍历执行整张看板、把讨论当作开工、改变现有公开性或分支策略。普通修改的长期自动提交授权仍取自该项目 `AGENTS.md`；明确交办的单次任务按本次授权执行，不据此写成所有任务的长期授权。
- 发布时机始终由用户决定，包括用户事先明确写下的发布条件。修复完成、检查通过、关闭 Issue 或里程碑完成都不自行触发版本标签、Release、安装包上传或发布工作流；用户只要求准备安装包时也不顺带发布。
- 同步前识别项目既有发布触发条件；若推送或合并本身会触发本次未获授权的发布，使用项目允许的非发布分支保存，或说明当前同步路径受阻。不能为完成同步擅自关闭既有工作流，也不能把发布副作用忽略掉。
- 仓库所有者、名称、远程及推送地址、分支、可见性、提交身份、检查/构建命令、版本文件、产物命名、看板链接/字段/事项分类及授权，都从当前项目读取；缺失项先由文件和现有配置推断。参考仓库与其私人看板均不是操作目标。
- 不覆盖用户或其他任务的未提交改动，不强制推送、不重写已发布历史、不绕过检查钩子，不自动切换成 PR 工作流。若涉及新操作，遵守本次任务范围。

## 共用检查与工具

- 在初始化或暂存前先检查目录、适用说明、技术栈、现有 Git 根目录/工作树、状态、暂存内容、分支与上游、远程的 fetch/push 地址。识别子目录、worktree、detached HEAD、进行中的合并/变基及冲突，不能将这些状态误作“没有仓库”。
- 查看有助于本次决策的 Git 配置及其来源，尤其是本地提交身份、默认分支、行尾、忽略规则、凭据助手、推送路由及钩子；只修改确需调整的项目级配置，不更改全局开关。输出配置时避免暴露带凭据的 URL、请求头或令牌。
- GitHub 先使用已连接且能力足够的工具；缺少创建仓库、附件上传等能力时使用已认证的 `gh` 或官方 REST API。没有 `gh` 不等于无法完成，不为流程额外强制安装 CLI。
- API 认证可复用当前任务对应的系统凭据助手；凭据只留在内存，不打印 `git credential fill` 的原始结果，不将令牌放进远程地址、提交文件或日志。若需要用户登录，只报告具体所需操作，不索要粘贴令牌。
- 需要确认 CLI/API 当前语法时，优先使用可用的 Context7 或官方文档；认证、权限与网络错误须区分于资源不存在，不以换账号、改公开或扩大权限来自动绕过。

## 检查后保存与同步

适用于已完成的一项用户任务，或用户明确要求保存的完整阶段。

1. **确定改动归属**：对照任务开始时的工作区和暂存区，只纳入本次相关改动；检查新增文件、忽略规则及敏感信息。已有暂存内容属于别人时保持原状，不能直接全部提交，也不能为了腾空暂存区将其撤下。若无法在保留它的情况下安全隔离本次提交，先处理可独立步骤并说明阻碍。
2. **完成必要检查**：读取项目的实际命令，按改动影响执行检查并记录命令、结果和必要数量；已有检查结果仅在对应改动未变化且适用时复用。检查失败先修复或报告，不把失败版本当作完成提交；纯文档按实际影响核验，不强制跑无关应用测试。用户明确要求保存临时进度时如实标注状态。
3. **核对暂存内容**：按文件或明确的改动范围暂存；核对暂存差异、文件名单、`git diff --cached --check`。不使用无差别暂存来夹带其他改动，不因目标是干净工作区而提交无关文件。无本次改动时不创建空提交。
4. **创建中文提交**：标题具体概括完整工作，正文说明主要改动、目的、实际检查及结果；未运行项说明原因。文件名、命令和技术标识可保留原文。每项任务通常一个提交，不按每次工具调用、一行改动或固定时间间隔提交；较长任务可保存值得独立恢复的完整阶段，GitHub 通常在任务完成时统一同步一次。
5. **同步指定上游**：提交前确认当前分支和真正的推送目标，沿用项目配置，不默认改成 `origin/main`。推送前如有远端并发更新，先获取并判断差异；不得自动拉取不相关分支、强推或重写来消除拒绝。推送失败保留本地提交，明确报告“本地已保存、GitHub 未同步”。
6. **远端核验与交付**：成功推送后读取远端目标分支，核对其包含本次提交；没有并发更新时应与本地 SHA 一致。若远端已前进，验证本次提交可从远端分支到达，不因 SHA 不同误报失败。报告必要检查、提交编号、同步结果及仍存在的其他改动，不把推送等同于构建、安装或发布成功。

提交、推送与正式发布是分别核验的状态。遇到可修复的临时错误可重试；失败后先回读实际状态，避免重复提交、重复创建仓库/Release 或覆盖附件。重复出现相同权限/状态冲突且无安全进展时报告具体阻碍，不无界重试。

## 项目约定如何保存

- `AGENTS.md` 保存当前项目的明确授权及上述具体参数，技能保存操作流程，README 提供面向读者的协作导航和简短约定；合并修改时保留已有 Issues/看板、验收及开发记录章节。不把参考仓库的看板、模块、所有者、私有路径、检查命令或平台参数直接套用到新项目。
- 用户要求项目沿用这套流程时，写入技能名称、仓库/上游、看板链接及状态含义、检查命令、必要发布参数及用户已明确授予的长期授权。仅初始化仓库的请求包含看板接入，但不能被改写为“以后所有修改自动推送”或“自动发布”。
- 技能不可用时仍可依据项目明确授权执行基础 Git 操作；不能靠缺失的技能引用推断新权限。必要流程不可读取时说明具体缺口。
