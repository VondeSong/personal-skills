# GitHub Release 发布

发布时机由用户决定：仅在本次请求明确要求发布，或用户事先指定的发布条件实际满足时执行。Issue 关闭、检查通过和里程碑完成本身均不是发布授权，不为它们自动创建发布标签或触发发布 Actions。使用项目已有发布方式；若标签会触发 Actions，由该工作流构建和创建 Release，等待它完成并核验，不能再并行手动创建竞争的 Release。

## 确定发布输入

- 从项目 `AGENTS.md` 和版本/构建文件读取版本、检查命令、发布分支与目标提交、标签/标题格式、产物目录及命名、目标架构、安装方式和正式版/预发布要求。默认标签 `vX.Y.Z`、中文更新说明、校验文件 `SHA256SUMS.txt`，项目明确配置优先；不能硬编码 CraftBridge 的脚本或 hub-search 的版本。
- 核对当前远程版本和实际差异。用户给定版本时保留；未指定时结合当前版本和变化提出合理版本，无法可靠推断再询问。检查代码、锁文件中本项目条目、安装说明、构建脚本和 EXE/包元数据，按平台规则保持版本一致。
- 将发布所需的源码及说明按主流程检查、中文提交并同步，固定完整提交 SHA。构建与打包针对同一源码状态；构建后再核对相关输入没有变化。本机未提交变更不能混进该提交名下的安装包。
- 先检查远程标签及同版本 Release。存在草稿时读取其目标和附件，可在核验后续传缺失文件；已发布同版本则验证现状并报告，不重复发布。标签解析到不同提交、附件同名但摘要不同等冲突需说明，不移动标签、覆盖附件或删除重建来消除冲突。

## 构建、安装包和校验文件

1. 执行项目真实的必要检查、正式构建和打包，检查每个命令的退出状态；不能因外层 PowerShell 脚本结束或目录里已有 EXE 就认定构建成功。锁文件使用项目支持的锁定模式；已有同版本产物只有经一致性核验后才复用。
2. 根据项目预期清单核对平台、架构、版本和完整安装内容，包括所需 EXE、安装/启动/卸载入口、说明、适配器及资源。对打包前后的关键二进制计算 SHA-256，确认包内确为本次正式构建；脚本与资源需对应发布源码。排除凭据、环境私有配置及运行数据。
3. 对最终上传的所有安装包计算 SHA-256，在项目输出目录写入 UTF-8 `SHA256SUMS.txt`，每行 `<小写 sha256>  <附件文件名>`，两个空格分隔，保留末尾换行。产物改变后重新计算；附件名使用实际上传名称。校验文件不自我收录。项目只发一个 Windows ZIP 时就列该 ZIP，不强制新增其他平台产物。
4. 保持产物、校验文件及生成的临时发布文案遵循项目忽略规则，不为上传 Release 将安装包加入源码历史。

## 中文说明

依据目标提交相对上一版本的实际变化编写，首发可概述现有功能。说明主要新增/修复、必要的兼容性变化、目标系统与架构、下载与完整安装/卸载方式、已知限制、源码 SHA 及附件校验方法；可附安装包摘要。不要只把提交标题机械列成日志，也不要虚构实机测试或安装验证。

文件名、命令和接口标识保留原文。版本、标题和附件名统一；若用户或项目已有明确授权，直接完成说明与发布，不为通用模板新增逐步审批。

## 上传、发布与回读

- **手动/API 发布路径**：先创建指向目标完整 SHA 的草稿，上传安装包和校验文件。核对每份附件的名称、上传完成状态、大小和服务端 SHA-256；服务端不提供摘要时下载后计算。私有仓库使用已授权下载方式，凭据不进入链接或日志。
- 全部验证通过后才转正式发布。新正式版标为非草稿、非预发布并设为 Latest；历史版本补发不替换最新版本，预发布不设为 Latest。使用项目已约定的标题，例如 `<产品名> vX.Y.Z`。
- **已有 Actions 路径**：确认标签触发条件和准确目标提交，等待相关工作流真正完成；校验其产物及发布状态。若工作流已创建 Release，则在核对后更新必要文案或补齐明确缺失附件，不能再创建同标签 Release。标签大小写依项目触发规则。
- 发布后回读中文说明、正式/预发布状态、Latest、所有预期附件及摘要；解析远程标签至 commit（附注标签需要继续解析），确认与目标 SHA 一致；同步标签到本地并检查工作区。
- 交付可访问的 Release 链接、版本、目标提交、检查与附件核验结果。私有发布仍受仓库权限限制，不为方便下载擅自公开。

## 失败与恢复

失败时先回读远程状态，保留本地安装包、校验文件和可恢复草稿，说明具体未完成步骤。安全重试只补齐尚未成功的操作；同名附件不一致、标签冲突、权限失败时不得盲目覆盖或重复创建。不能把本地标签、草稿或部分附件上传报告为正式发布完成。
