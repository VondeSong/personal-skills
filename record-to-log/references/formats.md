# 日志格式约定

输出本次日志前读取；本次任务已读且规范未变时可复用。适用于选择日志格式、批量整理、周期回顾和机器导入。用户指定的格式与目标系统已有规范优先；正文与机器数据都遵循主文件的事实、时间和状态边界。实际保存另读 [保存与外部技能适配](storage.md)。

## 默认：轻量 Markdown

可靠日期写在标题中；短日记可只写日期，有检索价值时再加入事件或对象名称。没有发生日期时，可用“时间未提供｜主题”，或在所在章节统一说明；不要重复填满“未知、无、待补充”。

```markdown
## 2026-10-11｜测试环境恢复

重启测试服务后，页面恢复访问。原因尚未确认，准备明天继续检查。
```

这是格式示意，使用时必须替换为源材料支持的内容。标题下直接写一段话即可；不强制“背景—行动—结果—反思—下一步”五段式。

不确定信息优先放在对应句子中。关键日期、对象归属或结论的歧义仍可能被误读时，在日志正文外补一句提示，例如“说明：旧聊天日期和发言人未知，未将经历归到你本人。”无需提问就能交付的整理稿先交付。结构化输出时，把这类信息放在相关字段或按需的 `notes` 中，保持 JSON 可直接解析。

当材料包含多个信息层次时，可按实际内容使用以下小节，不必全部出现：

- **记录**：行为、关键过程与观察。只有关键顺序时用列表，不自动生成时间线。
- **结果**：已观察到的结果及验证范围；没有结果就省略。
- **判断**：材料中的推测、反思或结论，保留说话者和确定程度。
- **待确认**：原材料已有或确实影响理解的歧义。一般性缺项不自动变成“待办”。
- **后续**：明确的计划、决定或承诺。负责人和期限仅在有来源时标明。
- **感受**：适用于个人日志；可以自然融入正文，不强制独立小节。
- **来源**：多来源、附件、关键证据或用户要求溯源时提供。引用实际可访问的来源，无法访问就说明。

小节名称尽量稳定，相同含义不随意切换叫法；个人记录仍可采用连贯叙述。保留事实与计划的区分比固定标题更重要。

## 精炼正文：按含义重写

- 先辨别独立信息，再组织成稿，不把每个原句都当成必须保留的一项。允许换用更准确简练的词语或常用成语、调整叙述顺序、拆合句子；不必贴着原话替换近义词。
- 同一感受或状态及其解释只表达一次。原文若用“确切地说”等纠正前面的泛泛说法，以澄清后的意思为准；若前后是事实变化、不同观点或时间上的反复，则仍分别保留。
- 省去口头填充、重复铺垫、语境明确的主语与没有新增信息的解释。保留承载情绪强度、犹豫或变化的意思，选用短词表达，不把感受删成纯事件清单。
- 按本次记录范围取舍。特定主题之外的闲聊可省略；记录一天时，独立事项和身体感受宜用短句保留。背景仅在删去后不影响理解时省略。
- 精炼后仍能分清对象、时间、行为、结果与感受。否定、推测、约数、暂时状态、复发、验证范围、说话者归属和“本想怎样、实际却怎样”的转折不能丢；必要的数值、单位和因果关系仍准确。只写“之后”不等于能改成“因此”。
- 用自然、紧凑的书面语交付，尽量让一句话承载完整意思；不靠生僻词、句意含混或速记缩略换取字数减少。只交付一份成稿，不附重复总结、改写说明或多版本，除非用户要求。

### 个人记录示例

原记录日期为 2026-10-11：

> 今天一天什么也没有做，确切的自己没有一个重心，不知道做什么。总觉得心情乱糟糟的。中午去办理了宽带，晚上吃过饭有点头晕，再次吃撑了，本来晚上不想吃了。克制不住自己的贪欲。
>
> codex跑了一天的hub优化。

可整理为：

> **2026-10-11**
>
> 一天无所适从，心绪烦乱。中午办了宽带，Codex 跑了一天 Hub 优化。晚饭本想不吃，却又贪嘴吃撑，饭后有些头晕。

这里将“没重心、不知道做什么”合成“无所适从”；“什么也没做”由其后的自我澄清承接，不另写成客观无活动。独立事项、主观感受、晚饭意愿与实际行为的转折、再次吃撑及饭后轻微头晕仍保留。该示例说明改写方向，不固定词汇或句数，不把每种低落情绪都写成“心绪烦乱”。

### 带限定信息的排查示例

原记录：“今天那个同步的问题我又试了，就是重启了一下，然后还是不行，可能是接口限流吧，但是我还没查日志。”

> 今天再次尝试重启，同步仍失败；怀疑接口限流，尚未查日志。

重复尝试、仍然失败、原因未确定和未查日志均不能删去，措辞可等义改换。检验标准是：成稿能否更少重复、更紧凑地承载原有实质信息，且读者对事实、状态、感受及其关系的理解保持一致。

## 按天、按事件与周期回顾

| 情况 | 组织方式 | 保留重点 |
|---|---|---|
| 同一天的零散事项 | 日期下分主题 | 独立事项与各自状态 |
| 一个事件持续多天 | 事件标题下列有依据的日期进展 | 每次尝试、状态变化、当前待解决点 |
| 多天且多主题 | 日期→主题，或沿用现有记录结构 | 不把不同日期折叠成同日完成 |
| 周/月回顾 | 明确覆盖时段，再归纳进展、变化、遗留事项 | 区分来源明确的事实与跨记录总结 |

回顾需要说明实际可用的记录范围，例如“依据 10 月 7 日、9 日和 11 日的三条记录”。数据不足以支持次数、时长、趋势或完成率时不生成这些统计。概括“反复出现”的问题应能定位到对应记录；不从沉默推断状态。

## 机器可读格式：按需启用

只有用户要求机器导入、批量加工、明确元数据规范或目标系统要求时启用。先适配已有格式；未有规范时使用下面的轻量约定。聊天中默认仍交付可读正文，不同时输出内容完全重复的 Markdown 和 JSON。

最小 JSON 记录包含 `schema_version`、`subject` 与 `entries`。`entries` 按来源支持的事件顺序排列；条目 `kind` 表明语义，不代表事实已经被第三方核实。

```json
{
  "schema_version": 1,
  "subject": "测试环境访问异常",
  "event_time": {
    "value": "2026-10-11",
    "precision": "day"
  },
  "entries": [
    {"kind": "action", "text": "重启测试服务。"},
    {"kind": "observation", "text": "重启后页面恢复访问。"},
    {"kind": "hypothesis", "text": "原因可能与连接数有关。", "attribution": "记录者"},
    {"kind": "plan", "text": "继续检查。", "scheduled_for": {"value": "2026-10-12", "precision": "day"}}
  ]
}
```

该示例展示结构，不是待记录的事实。字段规则：

| 字段 | 含义与使用条件 |
|---|---|
| `schema_version` | 本约定版本，当前为整数 `1`；已有目标规范则使用其版本机制 |
| `subject` | 有来源支持的可检索主题 |
| `entries` | 非空数组；各项包含 `kind` 和 `text` |
| `kind` | `action` 行为、`observation` 观察/反馈、`hypothesis` 推测、`feeling` 感受、`decision` 已作决定、`plan` 未来行动、`question` 原材料中的未决问题 |
| `attribution` | 说话者、观察者或记录者；第三方反馈、多人观点或身份易混时填写 |
| `event_time` | 整条记录确有共同时间才设置；跨日期时给各条目分别设定，不虚构一个共同日期 |
| `event_time.value` | 已知精度下的 ISO 日期/时间，如 `2026-10`、`2026-10-11`；时区已知的具体时间带偏移 |
| `event_time.precision` | `year`、`month`、`day`、`minute` 或 `second`，与来源精度一致 |
| `event_time.text` | 可保留“上周某天”“大约十点”等原始时间表达；无法可靠换算时只填本字段，省略 `value` 与 `precision` |
| `recorded_at` | 实际整理/保存日期或时间；仅在需要区分补记、审计或导入时提供，与发生时间分开 |
| `sources` | 按需列出实际来源对象，包含 `label`，有真实地址时再加 `url` 或 `path`；多来源时条目可用 `source_refs` 引用其实际 `id` |
| `notes` | 按需的字符串数组，承载日期基准或说话者未知等整理说明，与事件正文分开 |
| `id`、`related_to` | 持续保存或系统需要时分配/沿用；不要凭空引用不存在的记录 |

可选字段未提供时省略；导入接口要求固定字段时用 `null`，不要填“未知”冒充日期。布尔值不表示未核实；例如缺少完成证据不等于 `completed: false`。不强制给整条混合记录设置统一状态，状态直接在有对象、有时间的正文中表达。

计划的执行日期属于该 `plan` 条目的 `scheduled_for`，格式沿用 `event_time` 的时间对象；不放进该计划被记录/提出的 `event_time`。批量输出用 JSON 数组，只有用户或系统要求流式导入时才采用 JSONL。

Markdown 文件需要元数据时，可用 YAML frontmatter 放入 `schema_version`、`id`、`subject`、`event_time`、`recorded_at`、`sources` 等实际需要的字段，正文保持可读。日期、时间和 ID 使用引号，避免解析歧义。不要为了元数据在 frontmatter 复制一份完整正文。
