# Craft Page Visualizer

将当前 Craft 页面中的内容理解、提炼并转换为一个可编辑的 Craft Whiteboard。

核心目标不是单纯"画图"，而是：

> **根据内容本身，自动选择最适合的视觉结构，让这个页面比阅读原文更容易理解、记忆、复习和回顾。**

生成的白板必须是 Craft 原生 Whiteboard / Excalidraw 元素，而不是图片截图。

最终判断标准（贯穿全流程都要回头检查）：

> 如果用户半年后重新打开这篇笔记，只看这张白板，能不能在几十秒内重新回忆起核心结构？如果不能，就继续优化。

---

## 1. 前提条件

本 skill 可能在两种场景下被触发，先判断自己处于哪一种：

**场景 A —— 在 Craft App 内运行**：当前页面的 `pageId` / `documentId` 已经由调用上下文提供，直接使用即可，跳过下面的定位步骤。

**场景 B —— 通过 Claude.ai / Cowork 等外部环境连接 Craft API**：这种情况下没有"当前页面"这个概念，必须先定位到用户指的是哪篇文档：
- 如果用户给了文档名称、链接或明确指代（"这篇笔记"指的是之前讨论过的文档），先用 `GET /documents/search` 或已有的文档 ID 确认。
- 如果无法唯一确定，向用户确认一下具体是哪篇文档，不要猜。

其他前提：
- Craft Connect API 的 base URL 形如 `https://connect.craft.do/links/{spaceId}/api/v1`，鉴权 Token 从 Craft App 的 API 设置里获取。
- **Whiteboard API 目前是 Experimental API，字段可能变化。** 调用前后都要以当前实际可用的 API/工具 schema 为准，不要凭空假设或编造字段名；不确定时先用 `GET /whiteboards/{id}/elements` 读一次已有数据，观察真实字段结构再动手写。

---

## 2. 核心原则

白板的评价标准不是"是否把原文全部放进去了"，而是"是否让用户比阅读原文更快理解它"。

1. 理解优先 —— 先懂内容，再画图
2. 结构优先 —— 图形结构服务于内容逻辑，不是反过来
3. 记忆优先 —— 帮用户几十秒内重新建立认知
4. 主干优先 —— 抓大放小，不追求完整
5. 简洁优先 —— 控制节点数量和文字长度
6. 忠于原文 —— 不编造原文没有的关系或结论
7. 可编辑优先 —— 输出必须是原生 Excalidraw 元素，用户能直接改
8. 视觉层级优先 —— 用强调而非颜色堆砌表达重要性

不要机械地把页面中的每一段文字变成一个节点。

## 3. 总体执行流程

```text
① 确定 pageId / documentId（见第1节）
② 读取页面内容与已有 whiteboard block
③ 建立内部知识模型（不要立即画图）
④ 判断最合适的图形类型
⑤ 计算节点、连线与布局，先构造完整 elements[]
⑥ 本地预检 ID / index / 坐标 / 层级 / 重叠 / 文字尺寸
⑦ POST /whiteboards → 保存 whiteboardBlockId
⑧ 批量 POST /whiteboards/{id}/elements 写入
⑨ GET elements + GET 目标页双重校验
⑩ 如有明显问题，恢复同一个 whiteboardBlockId 并用 PUT 调整
⑪ 简洁反馈给用户
```

明确禁止跳过中间步骤直接"读取内容 → 生成大量节点"。理解 → 抽象 → 结构化 → 布局规划，这几步不能省。

---

## 4. 第一步：读取页面内容

尽可能递归读取当前页面能访问到的完整内容：标题层级（H1/H2/H3）、正文、列表与子列表、引用、Card、子 Block、表格中的关键信息，以及页面已有的结构。

如果页面内嵌了子页面：默认只分析当前页面正文中实际展开、属于当前页面的信息，**不要未经用户要求就递归分析整个 Space 或跳转到子页面**。

---

## 5. 第二步：建立知识模型，先别画图

读完内容后，先在内部构建一个"知识模型"，至少尝试识别：核心主题、关键概念、主要模块、实体、关系、步骤、因果、层级、时间、输入输出、结论、问题/原因/措施。

推荐的内部数据结构（把"理解内容"和"绘制 Excalidraw"这两件事彻底分离）：

```text
Diagram
 ├─ type        （图形类型，见第6节）
 ├─ title
 ├─ nodes[]      { id, label, summary, level, category, importance, variant, x, y, width, height }
 └─ edges[]      { from, to, relation, direction, certainty }
```

举例，原文：

```text
12V 蓄电池正极线连接前舱电器盒。同时一路连接 DCDC 保险丝盒。DCDC 向低压系统供电。
```

不要直接生成三个文本框，而是先抽象为：

```text
实体：12V 蓄电池 / 前舱电器盒 / DCDC 保险丝盒 / 低压系统
关系：12V 蓄电池 ├→ 前舱电器盒
              └→ DCDC 保险丝盒 → 低压系统
```

有了这个中间结构，再进入下一步选图形、算布局。

---

## 6. 第三步：判断图形类型

不要默认所有内容都生成思维导图——不同内容应该用不同的视觉结构。可选类型：思维导图、流程图、系统结构图、因果关系图、问题分析图（Root Cause）、对比图、时间线、层级树、混合知识图。

**每种类型的适用场景、关键词检测规则和示例结构，见 `references/diagram-types.md`。** 判断时可以内部给每种结构打分（层级分/顺序分/关系分/对比分/时间分/因果分/系统分），取分数最高的类型，但不需要向用户展示打分过程。

原则：
- 一个白板只能有一个主要视觉逻辑，不要多种图形堆在一起造成混乱。
- 如果用户明确指定了图形类型（比如"生成流程图"），遵循用户指定，即便判断另一种类型可能更合适——但可以在这个类型内部优化结构。
- 页面内容同时具备多个明显结构时，可以做"混合知识图"（一个主结构 + 局部子结构），细节见 references 文件。

---

## 7. 第四步：信息压缩与节点数量

白板不是正文副本。推荐压缩比例：正文 100% → 结构化知识 30%~50% → 白板文字 15%~30%。一个节点只承载一个思想，不要把一整段话塞进一个节点。

节点数量参考：
- 简单页面：5～12 个知识节点
- 中等页面：10～25 个知识节点
- 复杂页面：20～40 个知识节点
- 极复杂页面：优先压缩，通常不超过 50 个主要知识节点；如果页面信息量明显超出单张白板承载范围，优先生成一张 **Overview**（只保留核心主题、一级结构、重要关系、关键结论），不要为了"完整"生成超大蜘蛛网。

信息层级默认最多 4 层：Level 0 核心主题 → Level 1 核心模块 → Level 2 关键知识 → Level 3 必要细节。

注意：一个知识节点通常对应多个 Excalidraw element（矩形 + 文字 + 连线），所以最终 element 数量会明显大于知识节点数量，但知识节点数量才是控制信息密度的关键指标。

具体的压缩示例见 `references/examples.md`。

---

## 8. 第五步：布局与视觉规范

计算布局前，先确定：每类节点的默认尺寸、节点间距、连线该不该画、要不要加标签、要不要用颜色/强调区分重要性。这些具体数值和规则见：

- **`references/layout-rules.md`** —— 节点默认尺寸、间距、思维导图/流程图/系统图各自的布局方向与排布方式、如何避免节点重叠。
- **`references/visual-style.md`** —— 连线的语义（连线代表真实关系，不是装饰）、不确定关系的处理（标"待确认"而不是编造）、连线标签用词、颜色与强调的语义化用法、整体视觉风格（简洁克制，不做信息海报）。
- **`references/card-design-system.md`** —— 当白板包含 3 个以上卡片或用户要求优化视觉时必须读取；规定专业轻量卡片、变体、中文排版、8 点栅格与视觉验收，并说明 `scripts/craft_whiteboard_design.mjs` 的用法。
- **`references/apple-editorial-whiteboard.md`** —— 用户提出界面乱、UI/色彩不好看、Apple 风格或截图重排时必须读取；规定减卡片化、语义色、连接线降噪与截图复盘方法。

核心红线：
- 连线必须代表原文能支持的真实关系；原文无法证明的关系，宁可不画，或明确标注"待确认"。
- 不要随机摆放坐标，必须先算好布局再调用 API。
- 避免大量交叉线：如果节点间存在大量 many-to-many 连接，只保留对理解最重要的关系，次要关系用分组/空间邻近来表达，而不是把每条线都画出来。
- 默认卡片使用可辨认的中性边界和明确文字层级；核心、持续对比类别、风险、结论可使用低饱和浅色面。分类色必须稳定并配合标签/位置，普通节点不要每张一种颜色。
- 优先使用 `scripts/craft_whiteboard_design.mjs` 生成卡片和文字尺寸；提交前运行其 `audit()`。若不使用该脚本，也必须满足相同的标题两行、摘要三行、最小字号、颜色数量与重叠检查。

## 9. Craft Whiteboard API 用法

| 操作 | 接口 | 说明 |
|---|---|---|
| 创建白板 | `POST /whiteboards` | 参数 `pageId`、`position`（`"start"` \| `"end"`，默认 `"end"`）。响应返回 `whiteboardBlockId`，后续所有操作都依赖这个 ID，必须保存。 |
| 读取元素 | `GET /whiteboards/{whiteboardBlockId}/elements` | 返回 `elements` / `assets` / `appState`。用于检查已有内容、增量更新前的读取、生成后的校验。 |
| 追加元素 | `POST /whiteboards/{whiteboardBlockId}/elements` | 请求体 `{ "elements": [] }`。单次 ≤ 500 个 element，超出需分批提交（正常情况下本 skill 不该生成这么多）。 |
| 更新元素 | `PUT /whiteboards/{whiteboardBlockId}/elements` | 每个待更新元素必须带已有 `id`；只更新提交的字段，未提交的元素保持不变。用于修文字、调位置、改样式、修正布局。 |
| 删除元素 | `DELETE /whiteboards/{whiteboardBlockId}/elements` | 请求体 `{ "elementIds": [] }`。默认不删除用户自己创建的元素。 |

给每个新创建的元素分配唯一 ID，建议格式 `viz-{runId}-{type}-{index}`（例如 `viz-a81f-node-02`）。这个前缀很关键：后续"重新生成"或清理时，可以靠这个前缀准确识别哪些元素是本 skill 生成的，避免误删用户手动添加的内容。同一白板内严禁 ID 冲突。

元素的 `index` 同时控制层级和顺序，不能用普通字母表或随意字符串生成。新建/追加时优先使用本 skill 的稳定写入器生成合法 index，并按 `背景/框架 → 连线 → 形状 → 文字` 排序；更新已有元素时默认保留原 index。具体写入流程和脚本用法见 `references/api-write-workflow.md`。

批量策略：不要每个节点单独调一次 API。先在内存里构建完整的 `elements[]` 数组，再尽量少地提交；每批同时受 400 元素和约 64 KiB JSON 请求体限制，以先达到者为准。失败后只补同一白板的缺失元素，不重建第二张白板。

## 10. 第六步：创建、写入与校验

标准新建流程：确定 pageId → 读取内容与已有白板 → 建立知识模型 → 判断图形类型 → 计算布局 → 构造并预检完整 elements → `POST /whiteboards`（默认放在当前页面末尾，`position=end`）→ 立即保存 `whiteboardBlockId` → `POST .../elements` 写入。通过 API 写入时必须读取 `references/api-write-workflow.md`，优先使用 `scripts/craft_whiteboard_write.mjs`，不要每次临时重写提交逻辑。

**写入后必须双重校验**：`GET /whiteboards/{id}/elements` 检查元素 ID、字段、坐标、文字和数量；再 `GET /blocks?id={pageId}&maxDepth=1` 确认该 whiteboard block 挂在目标页面。若写入中断，先读取同一个 whiteboard 的已有元素，只补交缺失 ID 一次；不得直接再次创建白板。若仍失败，报告 `whiteboardBlockId` 和缺失 ID，停止自动重试。

---

## 11. 已有白板 / 更新 / 重新生成

**默认行为**：为本次可视化新建一个 Whiteboard，避免未经确认就改动用户已有的白板。

**用户明确要求"更新这个白板/优化这个图/继续这个白板"时**，进入 Update 模式：`GET` 已有 elements → 理解现状 → 保留有价值的元素 → `PUT` 修改需要调整的部分 → 必要时 `POST` 补充新元素 → 必要时 `DELETE` 清理本 skill 之前生成的冗余元素（通过 `viz-` 前缀识别）。不要重新创建第二个重复白板。

**用户明确要求"重新生成/不要原来的/重做这个白板"时**：读取旧元素 → 只删除能确认属于自动生成区域（`viz-` 前缀）的元素 → 重新 Add。如果无法可靠区分哪些是自动生成、哪些是用户后来手动加的，优先选择新建白板而不是冒险删除。

删除操作前必须确认目标属于本 skill 生成的元素，或用户明确要求删除；**默认禁止批量清空整张白板**。

## 12. 边界情况

- **页面内容很短或本身没什么结构**（比如只有一两句话、一个简单待办列表）：如实告诉用户"这篇内容比较简短，可视化的收益可能有限"，可以仍然生成一个精简的小白板，但不要为了凑数硬造节点和关系。
- **页面已经有一张白板，但用户只说"生成白板"、没说"更新"**：不要默认无脑新建导致白板堆积。先提示用户"页面里已经有一张白板了，是要新建一张，还是更新这一张？"——除非上下文明显是要新增一个独立的可视化角度。
- **无法可靠判断某个关系是否存在**：不要擅自连接节点表达确定关系，标"待确认"，或者干脆不画这条线。
- **页面内容极其复杂，远超单张白板承载能力**：优先生成 Overview（只保留核心主题、一级结构、重要关系、关键结论），必要时可以在同一张白板内划分多个视觉区域，但所有区域必须围绕同一个页面主题，不要为了"完整"生成超大蜘蛛网。
- **用户指定了具体图形类型**：遵循用户指定，不要因为 Agent 判断另一种类型"更合适"就擅自更改。

## 13. 生成前自检

调用 API 前检查：
- [ ] 是否理解了页面主题
- [ ] 是否提取了核心结构
- [ ] 是否选择了合适的图形类型
- [ ] 是否删除了重复信息
- [ ] 节点是否过多、每个节点是否足够短
- [ ] 是否存在原文不支持的编造关系
- [ ] 是否已完成布局计算（而不是随机坐标）
- [ ] 是否存在明显的节点重叠
- [ ] 标题是否不超过 2 行、摘要是否不超过 3 行；正文是否未小于 16
- [ ] 同层卡片的宽度、内边距、圆角与字体层级是否一致
- [ ] 缩略总览下是否仍能区分 Primary / Secondary / Tertiary；是否避免过度低对比
- [ ] 非中性色是否克制；风险、结论和待确认是否使用了正确语义色
- [ ] 元素 ID 是否唯一，坐标/宽高是否为有限数值
- [ ] 层级是否为：连线在节点后方、文字在形状前方
- [ ] 页面是否已有白板；本次是新建还是更新是否已确定

## 14. 生成后自检

写入并 `GET` 校验后检查：
- [ ] 核心主题是否明显、第一眼能否看懂
- [ ] 阅读顺序是否自然、主次是否清楚
- [ ] 是否有节点重叠或大量交叉线
- [ ] 是否有文字过长的节点
- [ ] 核心主题是否在 3 秒内可识别；分区背景是否弱于卡片
- [ ] 是否存在被截断文字、过度留白或卡片高度失衡
- [ ] 连线是否走留白通道，且没有穿过文字或无关卡片
- [ ] 是否存在无意义节点
- [ ] 是否比原文更容易理解、有助于记忆
- [ ] 所有提交 ID 是否回读存在，update 字段是否一致
- [ ] 新建的 whiteboardBlockId 是否确实挂在目标页

任何一项答案是否定的，用 `PUT` 继续优化，直到满足为止。

---

## 15. 禁止行为

- 机械复制原文（一段正文对应一个卡片）
- 不管内容是什么都强行生成思维导图
- 编造原文没有依据的关系
- 大量视觉装饰，把知识白板做成信息海报
- 擅自删除用户原有白板内容，尤其是直接清空整张 Whiteboard
- 修改页面正文（除非用户明确要求，只读不改）

---

## 16. 完成后如何反馈

成功后简洁告知即可，不要把内部推理过程（打分、候选方案对比等）讲给用户听，例如：

> 已根据当前页面内容生成白板。我将内容整理为「系统结构图」，重点保留了核心模块、主要关系和关键结论。

**但如果页面比较复杂**（节点数落在"复杂/极复杂"档，或者你对图形类型的选择本身没有太大把握），在这句话基础上补一句具体说明保留/舍弃了什么，方便用户判断要不要立刻要求调整——例如"原文里 XX 部分的细节做了压缩，如果需要展开可以告诉我"。简单页面不需要这一步，保持默认的零摩擦体验。

## 17. 默认任务指令（可直接作为内部执行提示）

> 阅读当前 Craft 页面的全部内容，理解页面主题、概念、层级、流程、因果、关系、时间顺序以及关键结论。根据内容本身自动选择最适合的视觉表达形式，而不是固定生成思维导图。将原始页面压缩为更适合理解和记忆的知识结构，然后使用 Craft Whiteboard API 创建一个新的 Whiteboard，并通过 Add Whiteboard Elements 写入可编辑的 Excalidraw elements。默认把 Whiteboard 放在当前页面末尾。不修改原正文，不机械复制原文，不臆测页面中不存在的关系。控制节点数量和文字长度，确保主次明显、布局清晰、连线尽量不交叉。创建完成后读取 Whiteboard elements 验证结果；如布局存在明显问题，则使用 Update Whiteboard Elements 修正。最终目标不是最大程度保存原文，而是让用户能够通过这张白板更快理解、建立知识结构并强化记忆。
