# 从设计原则到完整应用场景

**用途：生成完整页面、相连页面或可交互原型时使用的候选方法。** 沿用 [SKILL.md](../SKILL.md) 的平台范围、规则强度与现有产品约束，不要求所有应用采用相同布局或同时具备本文所有场景。

**整理日期：2026-11-12。** 本文把已有平台、视觉、组件和状态指导组织成可实现的场景规格；这些配方是设计建议，不是 Craft、Claude 或 Codex 的内部实现说明，也不证明生成结果已经达到其产品质量。

局部调整只读取相关段落。例如修复焦点、颜色或一句文案，不需要重新设计整个应用。原生组件和项目现有设计系统优先；仅在缺少相应决策时使用本文的候选起点。

## 1. 先明确要生成什么

从用户要求、已有界面与项目读取以下信息；缺少但不妨碍工作时，明确合理假设并继续。只有会实质改变方案的缺失才需要询问，不把填写一整张表作为开始工作的门槛。

| 决策 | 需要落到具体内容 |
| --- | --- |
| 主要活动与对象 | 人要完成什么，处理的是文档、内容块、会话、任务还是文件改动 |
| 现有结构 | 已有目的地、工具、组件库与品牌；哪些关系必须保留 |
| 目标表面 | 原生 Apple、明确 Apple 启发的 Web／跨平台；支持的输入与实际窗口 |
| 交付类型 | 设计规格、静态画面、可运行原型或产品实现；各自的验证能力不同 |
| 内容样本 | 使用有意义的中文标题、正文、状态、来源和长内容；示例数据明确标注 |
| 主要视觉方向 | 希望借鉴哪种具体关系：文档排版、对话阅读节奏、工作台密度或浮层层次 |
| 能力边界 | 哪些操作已真实支持，哪些在原型中模拟，哪些仍依赖未实现的服务 |

把“像 Craft／Claude／Codex 一样精致”翻译为可比较的设计方向。例如，以内容阅读与上下文工具为主，或以对话及结果为主，或以高效审阅与执行上下文为主。只选与当前任务相关的参考特征；不要机械拼接三个产品的所有区域。

缺少参考截图时，可以依靠现有规则提出候选方案，并标明尚未进行视觉对照；不把获得三款产品的全部实机素材作为设计的前置条件。涉及精确复刻或平台特定行为时，再补充对应证据。

## 2. 把一个任务写成相连的场景

完整场景至少解释开始、完成与再次进入。用下表中的相关字段组织规格；它是检查工具，不要求最终答复固定采用同一模板。

| 字段 | 要说明什么 |
| --- | --- |
| 任务与对象 | 用户目标、当前对象及操作范围；对象在页面变化后如何保持一致 |
| 入口与前提 | 从哪里进入；首次使用、已有内容、从通知或深链接进入有何差别 |
| 页面与组件 | 哪些区域同时可见，哪些逐层进入；各区域承担什么职责 |
| 用户动作 | 选择、输入、打开工具、确认或返回分别改变什么 |
| 即时反馈 | 按下、选择、输入、加载如何可见，焦点和滚动是否变化 |
| 结果与状态 | 什么时候可以说完成；加载中、空结果、失败和结果未知如何区分 |
| 纠正与恢复 | 撤销、重试、改输入、恢复草稿的作用范围与可用条件 |
| 退出与继续 | 关闭面板、返回列表、切换对象后保留哪些内容与位置 |
| 两端与主题 | 窗口收窄如何重排，相关状态如何适配浅深主题与文字放大 |
| 验证证据 | 哪些只是规格，哪些有实际画面、操作记录或设备测量支持 |

**填写示例：重命名文档。** 从当前文档标题进入编辑；保留文档标识和正文；聚焦标题并保留可取消的原值；提交后更新标题与相关列表项，保存失败时保留输入并给出局部重试；取消恢复旧标题；返回列表仍选中该文档。桌面可使用原位编辑或已有面板，手机根据键盘与空间选择合适容器；不能为了移动适配新建另一个同名文档。

这个例子说明规格的粒度，不要求所有重命名都采用相同形式。动作是否合法、怎样持久化和可否撤销，仍由实际产品决定。

## 3. 将组件和视觉角色组合起来

先复用 [组件说明](../COMPONENTS.md) 与现有库，再为当前场景建立小范围的组合约定。至少把结构、视觉角色和相关状态连起来；不要只罗列“侧栏、卡片、输入框、玻璃”。

| 组合 | 结构与关联 | 视觉角色和关键状态 | 窄窗口处理 |
| --- | --- | --- | --- |
| 导航＋标题区 | 目的地、当前位置和当前对象相互对应；标题旁动作只作用于相关范围 | 当前目的地、键盘焦点与普通项可分辨；标题与辅助信息层级一致 | 采用项目已有导航容器，保留位置含义 |
| 列表＋详情 | 查询、筛选、选中对象与详情关联；返回可恢复列表上下文 | 普通行、选中行、悬停／按下和焦点分别表达；空库、无结果、加载失败区分 | 从并列改为逐层进入，保持对象与筛选 |
| 文档＋上下文工具 | 工具由光标、文字选区或块选择决定 | 编辑目标、选择范围及可用工具清楚；保存提示不挤动正文 | 工具不依赖悬停，键盘出现后仍能编辑 |
| 会话＋输入区 | 消息、附件、当前上下文与待发送内容保持关联 | 输入、发送、流式输出、停止和局部失败有可见区别 | 保留阅读与输入空间，长内容按需展开 |
| 结果＋证据／改动 | 摘要能进入具体来源、文件或差异；动作指向明确对象 | 未审阅、已处理、失败和不可用分别解释 | 摘要、证据和操作有连贯返回路径 |
| 菜单／面板＋触发器 | 临时工具能回到发起它的对象 | 打开、关闭、焦点与禁用原因清楚；模态与非模态行为分别处理 | 根据任务与可用空间调整容器，不连续堆叠面板 |

### 视觉绑定

为被采用的组合指定实际使用的颜色、文字与几何角色。自定义 Web 可从 [TOKENS.json](../TOKENS.json) 的 `bgCanvas`、`bgContent`、文字、选中、强调与状态配对中选择；原生映射到平台语义角色。沿用 [Token 合约](tokens.md)，不要将装饰分隔线当作唯一的控件边界。

例如，列表选中可使用 `selectionBg`／`selectionText`，键盘焦点另用可辨识的焦点指示；同一对象进入详情后延续名称、状态和强调含义。需要一个新表面或状态时，记录其用途与前景配对，避免每个组件自行挑灰色。

为同一屏指定文字档位、图标家族与视觉重量、边界方式、内外间距和圆角关系。现有值可以直接作为起点，但不能只抄数值而忽略长标题、真实内容和相邻组件。桌面与手机共享角色，分别调整密度、行宽及触控空间；具体视觉分析见[视觉专项方案](desktop-mobile-visual-style-initial-plan.md)。

## 4. 内容浏览与持续编辑

用于文档、笔记、资料库和其他内容创作。若任务只需阅读或简单文本输入，不额外引入块编辑器、命令菜单或复杂多选。

### 建议的场景范围

库／集合或检索结果进入文档，阅读并定位内容，选择文字或对象，执行相关编辑，得到准确保存反馈，能够撤销或恢复，再返回原来的内容位置。

| 阶段 | 需要作出的设计决定 |
| --- | --- |
| 查找与进入 | 区分全局检索、当前集合筛选和文档内查找；结果说明对象及命中位置；返回保留查询与位置 |
| 浏览与编辑 | 点击、双击、进入编辑或使用已有入口分别有什么作用；当前是否编辑应容易理解 |
| 选择与工具 | 区分文字选区、单块、多个对象；相关工具跟随当前目标，工具操作后保留合理选择与光标 |
| 插入与格式 | 使用现有编辑器支持的动作；若有斜杠菜单或格式面板，说明打开、筛选、选项、退出及输入恢复 |
| 多选与整理 | 显示范围及可用操作；操作作用于选择集，成功与失败项分别保留；单个删除与批量删除不能混淆 |
| 保存与纠正 | 区分编辑中、本机保存、待同步和同步结果；撤销恢复什么由真实能力决定，不用提示文案代替持久化 |
| 离开与回来 | 保留需要保存的草稿和对象位置；必要的离开决策只在确有未保存风险时出现 |

桌面可以利用并列区域、键盘和上下文菜单；手机提供可发现的触摸入口，并检查选区、键盘与编辑工具的关系。拖动可提速，但相关操作应有适当替代；高密度编辑工具不必为了美观全部隐藏。

**可验证片段：** 输入一段含中文与英文的长标题，选择部分正文应用格式，再取消菜单并继续输入；删除一个对象后撤销；从检索结果进入文档后返回。检查操作范围、选择、草稿和列表位置是否连续，而不只检查首页外观。

## 5. 对话与 Agent 会话

用于助手、问答与有执行能力的会话。对话本身的阅读与输入行为，在任务运行状态之外还需要单独设计。

### 页面组合

根据任务安排会话位置、消息流和输入区。输入区清楚表达当前资料范围、附件及必要设置；只有产品需要时才加入模型、速度或高级参数选择。消息区区分用户输入、回复、工具执行摘要和结果，避免所有信息使用相同的气泡与强调。

| 阶段 | 候选交互与状态约定 |
| --- | --- |
| 起草 | 草稿归属当前会话；切换会话后恢复对应内容；中文组合输入不误发送，多行输入行为明确 |
| 添加附件 | 区分准备中、可发送、上传失败及已移除；明确是否允许部分附件发送，未就绪项不能假装已送达 |
| 发送 | 显示已提交的消息与实际确认状态；避免连点产生重复提交；失败时保留可恢复内容并定位失败对象 |
| 流式回复 | 内容逐步出现，结构稳定；代码块、来源和工具结果随数据就绪呈现，不用虚构百分比表示进度 |
| 阅读旧内容 | 用户仍在最新位置时可跟随新内容；用户上翻后保留阅读位置，通过可见入口返回最新内容 |
| 查看结果 | 长工具输出、文件或引用按需展开；展开后能回到原消息和合理阅读位置 |
| 停止与继续 | 停止请求、已确认停止和已产生内容分别表达；继续、重试或重新生成的作用范围清楚 |
| 修改旧输入 | 仅在产品支持时提供；说明会改变哪个后续分支或生成结果，不静默丢弃已有结果 |
| 结束与错误 | 保留可读的部分输出；区分回复失败、工具失败和连接状态未知；下一步对应实际可恢复范围 |

“正在生成”和“正在执行工具”可以分别表达，但不把所有内部日志默认展开。关键状态变化需可被读屏感知，避免逐字流式更新或每条日志连续打断；遵循[验收指南](acceptance.md)和实际平台能力。

手机键盘、页面生命周期与远端任务执行的关系，继续使用[移动方案 §6–7](mobile-cross-platform-initial-plan.md#6-键盘与编辑状态)。关闭会话页面、停止生成和撤回已执行修改具有不同含义，不用一个关闭按钮同时承担。

**可验证片段：** 一条包含附件的消息发送失败，修正后重试；回复生成时上翻旧消息，再回到最新；停止后仍可阅读已有内容；局部工具失败不抹掉已经成功的结果。

## 6. 任务工作台与结果审阅

用于项目任务、AI 改动审阅、文件处理和其他需要跟踪结果的工作。沿用 [AI workflows](ai-workflows.md) 的阶段区分，不把分析结束当作动作已执行。

### 页面组合

以项目／任务定位当前上下文，用任务详情承载执行过程和结果，再将摘要连接到来源、改动或文件。桌面可并列展示，手机可逐层进入；具体栏数取决于可用空间与真实比较需求。

| 阶段 | 需要明确的关联 |
| --- | --- |
| 发起 | 目标、资料范围和执行位置可理解；发起动作与当前项目关联 |
| 跟进 | 当前阶段、需要用户处理的决定和已产生结果各有入口；不依赖始终展开日志 |
| 审阅 | 摘要能追溯到具体文件、对象和前后差异；选择与反馈不丢失 |
| 批准或应用 | 准确呈现当前选择、影响和动作范围；普通可逆操作不叠加无必要确认 |
| 局部完成 | 已完成、失败、尚未处理各自有计数和对象；重试只针对相应范围 |
| 纠正与历史 | 支持时提供撤销／历史；不能把取消执行描述成自动回滚 |

例如，12 项建议中选择 8 项执行，5 项成功、3 项失败，另 4 项未选择：界面同时保留这几组对象与下一步入口，不能把全部标为完成，也不能把重试默认扩大到已经成功的 5 项。数字只是示例，实际界面依据真实数据。

对代码 diff、表格或图片比较，可以保留必要的二维空间或专门比较视图。手机优先明确文件／对象、变化和操作范围，再进入细节；窄屏不能成为隐藏决定性证据的理由。

**可验证片段：** 审阅一个改动并提供反馈，切换对象后返回；执行部分选择并发生局部失败；只重试失败项；从结果进入具体证据再返回原任务。

## 7. 动效、材质与操作连续性

为实际涉及的变化作出运动决定，不把所有控件套用同一条全局动画。优先采用原生或既有组件的行为；自定义时记录触发、变化对象、起止关系、时序、再次操作如何中断，以及减少动态后的表达。

| 变化 | 连续性需要解释什么 | 减少动态或效果不可用时 |
| --- | --- | --- |
| 选择对象 | 选中落在明确对象上，焦点保持独立；不让列表整体跳动 | 直接更新选中与焦点提示 |
| 打开菜单／面板 | 与触发对象相关；焦点进入何处，关闭后回到哪里 | 保留位置、可读表面和正确焦点，无需大范围位移 |
| 列表进入详情 | 能理解当前对象与上层位置；返回恢复上下文 | 直接切换，同时保留标题、返回与对象关系 |
| 新内容到达 | 维持阅读位置，符合当前是否跟随最新内容的选择 | 更新内容或“查看新内容”入口，不强制滚动 |
| 侧栏收起／窗口变化 | 内容重排保持对象与操作可达，避免瞬间丢失选择 | 直接使用稳定的最终布局 |
| 删除／恢复 | 说明哪个对象被移除或恢复，相关计数同步，撤销条件真实 | 直接更新对象并保留必要反馈 |

自定义 Web 原型如果没有现成运动参数，可把约 140 ms 的小范围状态变化、约 220 ms 的面板过渡作为待比较起点；这不是 Apple 标准，也不是所有交互的统一时长。给具体动作选择属性与缓动，不使用 `transition: all` 代替设计。立即响应操作，不为播完动画延迟真实状态；重复操作可反向、中断或到达明确终态，避免排队播放过时动画。

为使用材质的组件说明背景内容、前景配对、层级与实色替代。Liquid Glass 主要用于导航／控制；内容区域可按需要使用普通表面或标准材质。网页模糊与透明只是近似；较大面积、长列表或动态背景需要在目标环境检查实际表现。检查项目与[移动方案 §8](mobile-cross-platform-initial-plan.md#8-材质动效与性能)一致。

需要性能验证时，记录实际设备／浏览器、数据规模、受影响动作与观察方法，先检查输入响应和滚动，再比较材质或动效的变化。未测量时不填写帧率、耗电或性能提升结果。

## 8. 交付与验证

### 交付最小但完整的一段体验

设计规格应让实现者知道对象、组件、动作、状态、恢复及视觉绑定。静态画面说明当前状态；可交互原型让主要路径和相关恢复真实可操作。原型模拟的数据或服务明确标注，不能将示例状态当作真实服务成功。

如果用户要求完整应用场景，交付一个有入口、有结果、能退出并继续的范围。不要只做一张首页，也不要默认扩建与目标无关的模块。样例窗口可以选桌面与手机的代表性 CSS 尺寸，但它们只是当前原型的比较条件；原生尺寸和项目断点分别确定。

### 验证三类不同问题

| 层次 | 观察什么 | 能据此说明什么 |
| --- | --- | --- |
| 规格完整性 | 沿着一个任务逐步走，检查动作对象、反馈、结果与恢复是否相互一致 | 方案能否指导实现；不能证明实际画面或运行通过 |
| 视觉一致性 | 同一内容和状态的桌面／手机、浅色／深色画面；真实中文、图标与层级 | 实际看见的视觉问题与比较结果；不能推断隐藏交互 |
| 运行连续性 | 实际操作编辑、提交、返回、恢复和相关键盘／读屏路径 | 已执行范围的行为；不能外推到未测平台或全部场景 |

可访问性与可用性之外，也明确说明视觉判断的依据：哪些元素争夺注意、哪一组文字或图标不协调、哪个表面没有说明关系。用具体画面与任务解释修改，避免没有证据的“高级感评分”。

维护 Skill 时，使用 [EXAMPLES.md](../EXAMPLES.md) 中相关输入做独立试生成，评价者保留检查条件；不要把预期答案直接放进试用提示。一次成功的文字方案仅验证部分指导能力。生成、观察、修正与再次检查共同形成质量依据，文档长度和来源数量都不能直接保证成品品质。
