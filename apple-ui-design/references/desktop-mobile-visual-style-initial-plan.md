# 桌面与移动端配色、样式与苹果式质感：视觉专项初步方案

**状态：视觉研究与候选设计方向，尚未转为正式样式规范或产品实现。**

**整理与来源核验日期：2026-11-12（北京时间）。**

本文补充[跨平台风格分析](cross-platform-apple-style-initial-analysis.md)和[移动端方案](mobile-cross-platform-initial-plan.md)，专门回答“桌面和手机的配色、字体、图标、圆角、阴影、玻璃及整体样式有没有充分考虑，为什么这些产品都有苹果气质却仍保持自己的美感”。阅读后应能提出可比较的视觉方案，而不只给出流程与兼容性建议。

生成相连页面或完整交互场景时，结合[应用场景与生成方法](application-scenarios.md)，把本文的视觉角色落实到组件组合、对象状态和操作连续性；视觉研究本身不代替具体场景规格。

**配色与整体观感的再次复核：** §4.4–4.6 补充视觉方向选择、主按钮与强调色的分工及两套可比较的候选色板；§5.1 明确工具文字与阅读文字可分别选档；§8.4 给出完整组合实例。可读取[候选配色数据](visual-presets.json)生成同一内容的浅深样例。

适用范围与规则强度仍以 [SKILL.md](../SKILL.md) 为准。保留 Skill 3.1 和现有 Token 合约；本轮没有调整应用代码、正式配色或线上原型。官方事实、设计解释和候选方向分别标明；对某个版本或平台的说明不能外推为全部客户端表现。

## 1. 现有视觉基础与本次补充

**判断：此前已经考虑视觉，但两轮研究没有把它展开为同样完整的桌面／手机视觉方案。** 现有 [TOKENS.json](../TOKENS.json) 已包含浅深主题、文字与状态配对、桌面／手机文字档位、间距、圆角、阴影和网页半透明预览值；[中文排版](chinese-typography.md)、[Web 指南](web.md)也已有相应要求。

缺少的是“怎样组合这些元素，以及怎样判断组合是否成立”。一个色板、字号表或圆角值不能独立说明界面为何精致。本轮补充以下关系：

| 视觉维度 | 需要回答的问题 |
| --- | --- |
| 基础配色 | 页面、导航、内容、浮层之间如何区分，整体偏中性、偏暖还是偏冷 |
| 色彩重点 | 品牌强调、当前选中、内容分类与状态如何各司其职 |
| 文字 | 标题、正文、辅助信息怎样形成层级，中文实际显示是否稳定 |
| 图标 | 笔画、视觉大小、留白和相邻文字是否协调 |
| 几何与密度 | 圆角、内外间距、组件高度和阅读宽度是否相称 |
| 层次与材质 | 分组、相邻、悬浮和遮盖如何表达，透明效果是否帮助理解 |
| 动态外观 | 悬停、按下、选中、焦点、窗口失活及面板展开是否连贯 |
| 两端一致性 | 哪些关系保持稳定，哪些参数按桌面／手机调整 |

这些是审视维度，不要求每个页面包含全部元素或固定数量的层级。阅读页、编辑器和数据比较页可以有不同密度与色彩。

**此次复核发现：**基础原则已有，实际生成仍可能停在同一套蓝灰示例。需补充的是明确的视觉取向、可执行的组件组合与实际画面观察，而不是继续增加抽象审美形容词或强制配额。

## 2. 产品与平台的一手证据

### 2.1 Craft：苹果借鉴与自己的视觉系统同时存在

**官方事实：** Craft 的工程文章说明，Fluid Segmented Control 受到 Apple Mail 在 WWDC 2024 展示的控件启发，随后由团队重新设计并实现；文章还记录了复选框跨浏览器与不同像素密度的打磨。[^craft-engineering]

**设计解释：** 借鉴可以发生在形状、选中反馈和变化连续性上，最终仍围绕 Craft 的文档、侧栏和内容组织形成自己的表达。这支持“有苹果气质”的观察，但不能由此推断整套界面来自 Apple。

**官方事实：** Craft 3.6.0 分别更新页面背景、文字、backdrop、块色、行内高亮和界面强调色，并对页面背景／文字组合提供可读性提示。这部分新配色明确标注 Mac、iPhone、iPad；同次更新还专门改善 Web／Windows 的中日韩字体显示与任务行间距。[^craft-colors]

**设计解释：** 精致配色是一组相互配合的角色；跨平台的文字打磨也属于视觉品质。不能将所有观感归因于使用某一款苹果字体。

**补充官方事实：** Craft 3.4.3 的 Web／Windows 更新将自选强调色映射到链接、选区、拖动高亮、Today 标题和图标徽记，并另行改善深色可读性。3.5.4 则明确将 Mac／iPhone／iPad Collections 的字段类型图标统一为 SF Symbols，数字／货币／百分比表格使用等宽数字。前者支持按角色设计强调色；后者说明精致感也包含局部图标与数字排列的打磨，不能外推为 Craft 全平台所有图标均来自同一个库。[^craft-accent][^craft-details]

**官方事实：** Craft 3.6.5 描述 macOS 侧栏与窗口表面的关系、中央文档的突出及侧栏对文档风格的吸收；iPhone 的深色界面与 iPad 全屏深色界面的应用背景，以及 iPhone 导航玻璃另作调整，收起侧栏时文档圆角也随窗口关系变化。[^craft-surfaces]

**设计解释：** 桌面与手机保留相近的视觉性格，同时分别处理表面、空间和材质。上述发布说明描述 Apple 客户端，不能据此断言 Android 或 Windows 具有同样的原生材质。

### 2.2 Codex 与 Claude：具体外观可变，产品关系仍可识别

**官方事实：** Codex 原 App Settings 官方入口当前重定向到 ChatGPT Learn 的桌面设置文档，其中说明基础主题、强调色、背景／前景色、UI 与代码字体可配置。这是当前桌面文档的能力描述，不能扩展为所有手机入口拥有同样的编辑选项。[^openai-appearance]

**设计解释：** 颜色和字体可以变化，而任务区、文字层级及组件关系仍能保持连贯。这是建立主题系统的有用参考；本研究没有取得 Codex 全部默认颜色、圆角和阴影的官方 Token。

**官方事实：** Claude 的外观帮助页提供浅色、深色、跟随系统及聊天字体选项；Claude Code 终端入口有单独的主题配置。[^claude-appearance][^claude-terminal]

**设计解释：** 讨论 Claude Code 的图形界面与终端时，需要保留入口差异。文字与语义颜色可以共同讨论，圆角、玻璃、阴影只适用于相关图形表面。外观相似不足以确认三款产品共用字体、SF Symbols 或内部设计系统。

### 2.3 Apple 与 Material 支持跨端保持颜色角色

**官方事实：** Apple 将动态系统色按背景、文字、链接、分隔线等用途组织；Material 3 也强调布局区域的颜色角色在断点变化后保持对应关系。Apple 的品牌指导允许通过颜色、文字语气、字体和内容表达产品身份，同时保留熟悉的平台组件。[^apple-color][^material-color][^apple-branding]

**设计解释：** 一套视觉语言能跨设备成立，是因为颜色、层次、形状和文字的关系可以保持连贯。具体值、面积和容器随设备改变，不妨碍产品仍被识别为同一个产品。

## 3. 苹果式质感的视觉构成

以下为本轮分析模型，用于解释用户的审美感受，不是厂商共同公布的设计公式。

### 3.1 表面之间的差异细腻，内容主次仍然清楚

相邻背景可以接近，通过适当的明度、色温、留白和边界让它们可区分；正文、次文字、选中与操作则保持足够清晰。这种处理可以同时带来轻盈感和稳定感。若背景、正文、图标、分隔线全部一同变淡，信息关系反而容易消失。

要比较的是整幅画面：侧栏是否压过正文、顶栏是否与内容抢注意、浮层能否被辨认。单个灰色看起来柔和，并不能保证组合后协调。

### 3.2 色彩有位置，也有不同职责

品牌色、内容本身的颜色、分类色和错误／警告等状态色可以共存。它们需要各自解释某种关系。照片、封面和文档背景可以承担丰富的色彩；工具层的色彩重量则根据内容和任务调整。

Apple 明确提醒，品牌色使用过广会削弱重点，并建议有意安排强调位置。[^apple-branding] 这不意味着所有界面都必须灰白、低饱和或只有一种彩色，也不构成“每页只能有一个强调动作”的规则。

### 3.3 文字和图标像一组经过整理的元素

标题有适当的分量，正文保持连续阅读节奏，辅助信息退后但仍可读；图标的笔画和视觉大小与文字协调。用户往往先感知整体节奏，随后才注意到某个具体字体或图标。

中文尤其需要使用真实内容检查：较长名称、全角标点、中英混排、数字及多行标题会改变画面节奏。直接缩小中文或统一使用极细字重，不能替代排版设计。

### 3.4 圆角、边距、轮廓和阴影属于同一组关系

外层容器、内层图片、按钮和窗口边缘需要比例协调；细边界和轻阴影分别表达相邻与悬浮。若每一行都加圆角卡片、每张卡片都加同一条明显阴影，画面容易出现过多同等强度的轮廓。

没有卡片的列表、白色阅读面、带颜色的封面和较密集的工具区都可以精致。容器应适合内容对象与关系，不能为满足某种风格而强行添加。

### 3.5 静态样式与状态变化保持连贯

悬停、按下、选中、焦点及面板展开沿用相同的视觉关系。变化应帮助理解对象和状态，而不是引入一套突然不同的颜色、形状或阴影。对桌面还要检查窗口失活后的表现，对手机则检查按下和触摸反馈。

这部分关注外观如何随状态变化。任务执行、断网和后台恢复等语义继续使用[移动端方案](mobile-cross-platform-initial-plan.md)，此处不重复展开。

## 4. 配色与浅深主题候选方案

### 4.1 先定义用途，再选择颜色

| 角色 | 候选处理 | 需要避免的混淆 |
| --- | --- | --- |
| 页面／窗口背景 | 承接整体色温与空间，不必成为最显眼的区域 | 背景颜色过重，使正文失去重点 |
| 内容表面 | 为文字、代码、列表或图片提供稳定背景 | 所有内容机械套用同一张装饰卡片 |
| 导航／工具表面 | 与内容可区分，同时保留产品的整体气质 | 侧栏和工具栏各用一套无关色温 |
| 浮层表面 | 让菜单、临时工具和面板容易定位 | 只靠透明或模糊效果区分，前景反而难读 |
| 主／次文字 | 根据内容重要性分配对比与字重 | 重要说明被处理成难读的小号浅灰字 |
| 强调色 | 标识相关操作、链接或品牌重点 | 所有图标、标签、按钮都使用相同强强调 |
| 选中与焦点 | 明确当前对象及键盘操作位置，两者可同时存在 | 用同一种不明显底色表达所有状态 |
| 状态色 | 与文字或图标共同解释成功、警告、错误 | 用品牌色替代所有状态含义 |

这些角色可由同一表面或同一颜色承担，不要求页面画出固定数量的灰色层级。具体组件继续遵守现有 [Token 配对合约](tokens.md)。

### 4.2 优先建立完整的浅色与深色主题

候选方向：先把白色／中性浅色和黑色／中性深色两套基础外观完整做好。若需要暖色阅读主题，再单独评估色温、强调色、正文和附件内容，而不只给整页覆盖一层暖色。

Apple 的深色指导明确说明，深色并非简单反相；部分平台通过不同亮度的背景表达前后层次。[^apple-dark] Craft 的纯黑手机背景是特定产品与平台的处理方式，不构成所有深色界面都必须纯黑的规范。

本 Skill 已有以下自定义网页／示意图配色，可作为比较起点。**它们不是 Apple、Craft、Codex 或 Claude 的官方色板，也不代表任何具体产品的配色。** 下表仅摘录，完整值与可用配对以 [TOKENS.json](../TOKENS.json) 为准。

| 现有角色 | 浅色值 | 深色值 | 视觉职责 |
| --- | --- | --- | --- |
| `bgCanvas` | `#F5F5F7` | `#121214` | 整体背景 |
| `bgContent` | `#FFFFFF` | `#1C1C1E` | 内容承载面 |
| `bgSecondary` | `#F2F2F4` | `#2C2C2E` | 次级表面 |
| `textPrimary` | `#1D1D1F` | `#F5F5F7` | 主要文字 |
| `textSecondary` | `#606066` | `#BCBCC2` | 次要文字 |
| `accent` | `#0066CC` | `#69B4FF` | 强调、链接或动作 |
| `selectionBg`／`selectionText` | `#E5F0FF`／`#003F88` | `#163D64`／`#D9EDFF` | 成对表达选中 |

候选评价重点是同一内容在两套主题中的关系是否稳定：正文仍是正文，选中仍明显，浮层仍有层次。蓝色是当前示例的强调色，不是“苹果式好看”的必要条件。

### 4.3 背景主题与强调色分别配置

若项目需要外观自定义，可将基础主题与强调色分开：主题控制背景、正文和表面关系；强调色控制相关交互重点。成功、警告、错误等语义继续保留自己的职责。

自选颜色影响配对时，需要重新检查强调色上的文字、浅深主题、选择背景与焦点。不能只替换一个 HEX 值就声称整套主题已适配；也不要凭背景名称如“夜读绿”推断其可读性。

### 4.4 先选定一套完整的视觉方向

新视觉设计或实质视觉重设计，应结合用户参考和现有产品，落下四个决定：**表面色温、颜色重点、工具与正文的文字节奏、边界与浮起方式。** 局部调整沿用原来的方向，不因本节重做整个产品。

把产品名转成具体借鉴对象：可以借鉴 Craft 对文档与侧栏关系的打磨、Claude 图形会话的阅读取向、Codex 工作台的内容与控制分工。后两项是本方案选择的参考方向，不能当作厂商统一配色或内部设计系统的事实；具体对照时注明实际表面、主题和素材日期。官网品牌色、终端主题、预览中被生成的应用，都不能自动当作宿主应用 UI。

| 候选方向 | 表面与颜色 | 适合优先比较的活动 | 应观察的偏差 |
| --- | --- | --- | --- |
| 柔白中性 | 接近白色的内容面、轻微偏冷的中性框架、少量蓝色链接／选中、中性实色主按钮 | 资料库、文档、并列工作与结果审阅 | 侧栏过灰、工具区过重、蓝色到处争夺注意 |
| 暖纸中性 | 轻暖的画布和阅读面、棕灰文字体系、有限的暖色重点、中性实色主按钮 | 长文、笔记、对话和较安静的阅读工作区 | 整屏泛黄、正文发灰、暖色重点与错误状态混淆 |

这两项是可比较的自定义候选，不是分别复刻某个产品。一个产品先保持连贯的基础方向；文档、会话、审阅可以改变密度与内容呈现，不必分别套一套互不关联的品牌外观。已有鲜明品牌、纯白或纯黑方案可以继续保留。

### 4.5 主按钮、强调色、选中与状态分别决定

中性实色主按钮也能有足够分量：浅色可用深色底、浅色字，深色可用浅色底、深色字。是否采用这种处理，取决于当前产品；彩色主按钮同样可以成立。不要把 `accent` 自动扩展成所有动作的填充色。

| 角色 | 两套候选中的具体处理 |
| --- | --- |
| 主按钮 | 使用独立的背景／文字配对，悬停与按下保持同一色系；数量和位置由任务决定 |
| 链接与必要重点 | 使用 `accent`，在正文中结合链接形态；需要强调色按钮时另用 `onAccent` 配对 |
| 当前导航／列表选择 | 使用 `selectionBg`／`selectionText` 并保留文字或形状线索；颜色面积不必与主按钮相同 |
| 悬停与按下 | 对当前对象进行小范围表面变化，不临时染亮整片侧栏或整张内容面 |
| 键盘焦点 | 独立指示，能与选中同时存在；在实色按钮周围留出可辨识的分离 |
| 成功、警告与错误 | 保留其语义配对、图标和文字，不被品牌换肤覆盖 |

表面分层可以依靠轻微明度差与留白，重要正文和控件仍要清晰。需要弱化视觉重量时，先检查面积、重复边框、过多容器和字重，而不是统一降低文字透明度。

### 4.6 可读取的浅深配色候选

[visual-presets.json](visual-presets.json)提供两套候选的浅深配对、行悬停／按下和中性主按钮状态。值仅用于自定义 Web 与示意图比较，**不是三款产品或 Apple 的官方 Token，也不替换现有 TOKENS.json。** 原生系统和项目已有配色优先。

| 方向／模式 | 画布 | 内容面 | 主文字 | 次文字 | 链接／强调 |
| --- | --- | --- | --- | --- | --- |
| 柔白中性／浅 | `#F4F5F7` | `#FFFFFF` | `#24262B` | `#61656D` | `#365F8C` |
| 柔白中性／深 | `#17181B` | `#1E2024` | `#E9EBEF` | `#B2B6BF` | `#A8C6EE` |
| 暖纸中性／浅 | `#F5F2EC` | `#FCFAF6` | `#2D2A26` | `#655E55` | `#8B4E34` |
| 暖纸中性／深 | `#1D1B18` | `#25221E` | `#EEE7DC` | `#BEB4A6` | `#E1AC86` |

使用时把 `paletteOverrides` 与现有对应模式合并作比较，状态配对继续沿用基础合约；`componentTokens` 是局部样例角色，需要显式映射到实际组件，不直接传入基础 Token 格式。高对比偏好、禁用、透明合成及项目新增颜色组合另行处理。

这两套候选的交互行标题与摘要／时间使用已检查的 `textPrimary`／`textSecondary`。`textTertiary` 只在基础中性表面配对中检查，不能据此假定它在较深的行按下背景上也合格；已有组件使用该角色时，需为相应状态选择兼容配对或另外验证。

**本次静态检查：**复用现有 `scripts/validate_tokens.py` 的不透明 sRGB 对比度计算，对两方向各自浅深模式的基础合约配对及 `componentPairChecks` 共检查 168 组，均满足声明阈值（文字 4.5:1，必要指示 3:1，判断时不四舍五入）。这只覆盖所列配对，不代表透明合成、全部组件状态或整页美感已经验证。

深色不要求处处纯黑：可以用邻近的深色表面承接内容，以较柔和的浅色文字维持层级。只将浮层和当前操作适当提亮，避免每个容器都成为醒目的灰块。上述仍是可比较方向，不能取代用户已认可的纯黑主题。

## 5. 字体、中文与图标

### 5.1 共享文字层级，分别调整阅读条件

**官方事实：** Apple 将字号、字重、行距组织成文本样式，并强调文字尺寸变化后仍能保持层级与可读性。[^apple-typography]

**候选方向：** 桌面工具界面可以较紧凑，手机需要为阅读和触控留出空间；长文与代码又有不同要求。标题、正文和辅助信息之间的关系可以共享，具体尺寸和阅读宽度分别调整。

现有网页档位已经区分桌面与手机：桌面正文参考 14／20 CSS px、标题 22／28；手机正文参考 17／25、标题 28／34（前者为字号，后者为行高）。这些是本 Skill 的可调示意值，不是原生 pt、屏幕截图像素或所有场景的最优值。原生映射到平台文本样式，已有项目样式优先。

**按角色选档，而不是整屏锁定一个档位。** 同一工作区可以使用 13–14 CSS px 的紧凑工具文字，同时让文档或会话正文采用 16–18 CSS px 与更舒展的行距。不要为了正文可读就把应用标题升级为营销页大标题，也不要把长篇阅读文字全部压到工具栏密度。具体组合示例见 §8.4；这些范围是起点，已有样式、窗口和文字放大要求优先。

字体选择之外，逐项比较中文真实字形、标点、混排、段落宽度、长标题换行和数字对齐。系统字体栈在不同平台会得到不同字体，仍可通过同一套层级关系保持产品气质；不能从观感推断各端都使用 San Francisco。

### 5.2 图标要做到视觉重量一致

**官方事实：** Apple Icons 强调细节、笔画、透视和视觉大小的一致，并建议图标与相邻文字的重量协调；不对称图标可能需要光学位置修正。[^apple-icons]

**候选方向：** 沿用项目现有的图标家族，检查侧栏、顶部工具和手机导航中的笔画、留白、基线与状态。相同外框尺寸不保证视觉大小相同。必要时小幅调整某个图标的大小或位置，而不是机械统一后忽略实际效果。

功能图标可以轻巧，封面、插画与内容图标可以更有性格；它们不必承担同样的视觉职责。选中表达可结合底色、文字或图标状态，但应保持语义稳定。没有一手证据时，不将 Craft、Codex 或 Claude 的图标归类为同一个库。

## 6. 圆角、边界、阴影与材质

### 6.1 圆角与间距一起确定

**官方事实：** Apple 在 WWDC25 讲解了内外形状的同心关系；胶囊适合触控布局，在密集桌面环境则更适合突出的动作，小型桌面控件仍使用较紧凑的圆角矩形。[^apple-geometry]

**候选方向：** 以组件大小、相邻边缘、内边距和嵌套关系选择圆角。外层面板、里面的图片及按钮不需要相同半径，但应形成协调关系。手机较大的控制面可以更圆润，桌面工具区保留较利落的形状；原生优先使用系统几何，网页值作为可调参数。

现有圆角档位可继续作为起点，不新增“全局统一大圆角”的强制规则。纯圆、胶囊、普通圆角和更平直的内容边缘都可以共存，只要角色与比例明确。

### 6.2 边界与阴影各自表达关系

候选方向：先用对齐、分组和留白说明内容关系；确需容器时用表面或边界区分。悬浮菜单、面板与临时工具再按实际层级配置阴影。暗色主题中，表面亮度与边界也参与层次表达，不能假定增加黑色阴影就一定有效。

Apple 对 Liquid Glass 的介绍也说明阴影会随背景与控件变化。[^apple-glass] 网页中的固定阴影只能提供某种近似，不代表具备同样的自适应行为。

现有 `separator` 只用于装饰分组；若边界是识别可操作控件的必要线索，应使用与背景配对的 `controlBorder` 或相应状态提示。轻边界不能以损失操作辨识为代价。

### 6.3 用材质说明导航与内容的关系

**官方事实：** Apple Materials 将 Liquid Glass 主要用于导航／控制层，内容层使用普通表面或标准材质；具体外观还需适应背景及系统设置。[^apple-materials]

**候选方向：** 桌面侧栏、工具栏和浮层，手机顶部／底部导航与临时工具，可分别比较轻材质的效果。正文、代码和长时间阅读区域需要稳定背景。屏幕内容没有产生值得透出的关系时，透明不一定改善画面。

原生 Apple 表面使用当前系统支持的组件；Android 与 Windows 沿用所在平台或项目的实现方式。网页 `backdrop-filter` 与半透明色属于视觉近似，不能声称等同原生 Liquid Glass。降低透明度、减少动态或不支持效果时，颜色和层级仍需成立。

## 7. 桌面与手机的统一及差异

| 维度 | 跨端保持的内容 | 桌面候选表达 | 手机候选表达 |
| --- | --- | --- | --- |
| 色彩 | 品牌与颜色职责 | 同时区分窗口、侧栏、主内容及相关面板 | 让页面、导航和临时工具在较小画面中清楚 |
| 文字 | 标题／正文／辅助信息关系 | 适应扫描、工具密度和较宽阅读区 | 适应近距离阅读、较窄行宽及字号变化 |
| 图标 | 图形性格、语义与状态 | 与较紧凑的工具和文字协调 | 图标可轻，实际命中区域充分 |
| 圆角 | 外形与嵌套的比例关系 | 小控件较利落，突出动作可更圆润 | 根据较大控制面与屏幕边缘安排几何 |
| 留白 | 对象内紧密、对象间清楚的关系 | 支持并列工作及有效密度 | 支持单列阅读、触控和必要分组 |
| 层次 | 相邻、分组、浮起、遮盖的含义 | 内容面与侧栏／检查面板相互协调 | 页面与导航／面板相互协调 |
| 状态 | 选中、焦点、禁用等含义 | 补充悬停、键盘焦点、窗口失活 | 补充按下和触摸反馈，避免依赖悬停 |
| 材质 | 内容与工具之间的关系 | 在窗口背景及较大表面中检查透明与阴影 | 在滚动内容及顶底导航中检查清晰度 |

这张表描述需要维持的关系，不要求两端具有相同布局或完全相同的颜色数值。是否出现侧栏、底栏、检查面板，应由现有信息架构和任务决定。

### 通用的候选落点

桌面可以让内容区域成为稳定的阅读与工作中心，侧栏和顶部工具保持清楚、适当的重量，相关细节在需要时出现。手机保留相同内容与视觉性格，重新安排字号、行宽、操作空间和导航表面。

示意内容可以使用“交付资料出现新版本—相关变化—来源”，通过标题、正文、来源链接及选择状态展示层级；不添加虚构的评分、百分比或无关仪表盘来填满画面。

本轮没有审查任何具体产品页面，因此上述是候选方向，不能写成已发现某个页面灰色过深、图标不统一或已完成修复。

## 8. 视觉样例与验证方式

### 8.1 用相同内容比较桌面／手机与浅色／深色

准备同一对象、相同信息和相同状态，分别观察桌面浅色、桌面深色、手机浅色、手机深色。保持内容一致，才能判断差异来自配色与布局，而不是不同示例内容。可切换主题的示意图用于讨论，不能替代原生材质或设备实测。

至少让画面中能看见标题、正文、辅助信息、当前选中及一个与任务有关的动作；这是比较样例的建议，不是每个产品页面必须包含这些元素的配额。

### 8.2 分别评价美感与实际可用性

| 检查角度 | 具体观察 |
| --- | --- |
| 整体视觉 | 是否容易找到重点，色温、边缘、文字与材质是否连贯 |
| 表面与色彩 | 相邻区域能否分辨，选中和状态是否清楚，自选强调色是否破坏配对 |
| 排版与图标 | 中文长标题、混排、图标重量、基线及文字放大后的效果 |
| 几何与密度 | 嵌套圆角与内边距是否协调，桌面是否过松，手机是否拥挤 |
| 主题与材质 | 浅深模式、真实背景、浮层、降低透明和减少动态后的表现 |
| 交互外观 | 按下、悬停、焦点、选中、禁用及窗口状态是否仍可辨 |

具体可读性、焦点、输入与读屏要求沿用[验收指南](acceptance.md)。对比度计算、截图检查、浏览器交互与实机验证分别报告；“看起来更像苹果”和“更适合任务”也分别讨论。

### 8.3 后续形成正式视觉方案所需内容

候选设计应给出：颜色角色与浅深配对、桌面／手机的文字及密度选择、图标使用方式、圆角与边界关系、浮层材质、相关状态，以及使用真实内容的两端画面。缺少其中某项时，明确它是否与任务有关或仍待验证。

先比较表面、排版、图标与几何的组合，再评估材质和动效带来的变化。一次只改变与待判断问题有关的变量，有助于理解改善来自哪里。最终根据用户偏好、任务和证据更新正式样式；本研究本身不自动替换已有 Token。

### 8.4 一个完成的视觉组合示例

**场景：中文资料与阅读工作区。** 保留既有资料导航、文档和相关操作；内容样本为《周末阅读与城市散步：把零散摘录整理成一页》。以“柔白中性”为首个比较版本，“暖纸中性”作为另一种外观，不让页面不同区域各自选择不同的整套主题。

| 部分 | 已作出的候选决定 | 两端与主题处理 |
| --- | --- | --- |
| 应用框架 | 画布及侧栏使用 `bgCanvas`，文档使用 `bgContent`；已有顶栏可以与内容共享表面，不强制增加灰色横条 | 桌面保留原有并列关系；手机逐层进入时沿用相同角色，减少无意义外框 |
| 文档与留白 | 文档正文宽度上限约 720 CSS px；正文外侧桌面约 32、手机约 20 CSS px | 窄窗口允许自然重排；不是把桌面整页等比例缩小 |
| 文字 | 工具 13/18、导航 14/20、文档标题 26/34、正文 17/28 CSS px；标题参考 600，正文 400，辅助信息 13/20 | 手机标题可从 24/32 起步；工具与长正文分别确定，沿用中文排版参考检查真实字形 |
| 当前对象 | 导航或文档行采用 `selectionBg`／`selectionText`；普通行保持其所在表面；悬停／按下使用局部行状态色 | 手机使用按下反馈；不把桌面悬停当作唯一可见线索 |
| 动作与链接 | 与任务相关的“整理摘录”可采用中性主按钮；正文来源链接使用 `accent`，普通工具使用正文／辅助角色 | 深色主按钮采用相应浅底深字配对；不是全页反相 |
| 图标 | 沿用一个现有功能图标家族，以约 16–20 CSS px 视觉尺寸与相邻文字对齐 | 可点击区域与图标图形分别决定；不将每个图标染成强调色 |
| 边缘与浮层 | 连续正文和普通行以对齐、留白组织；输入边界根据识别需要使用 `controlBorder`；菜单使用清楚的实色表面和适度阴影 | 暗色优先检查表面与边缘是否可分辨；大面积模糊不作为必要步骤 |
| 圆角与间距 | 小控件约 8、菜单／面板约 12 CSS px；相关工具间距约 8，分组约 16–24 | 看实际嵌套与空间调整；不把所有内容变成同半径的卡片 |

上述数值是一个完整例子的决定，不升级成全局固定值。已有编辑器、组件库和品牌优先。样例应同时呈现普通内容、选中对象、一个有关动作及其相关状态，检查它们是否像同一个产品。

### 8.5 直接观察“为什么还不够好看”

| 画面中观察到的问题 | 优先比较的调整 |
| --- | --- |
| 整页灰蒙蒙，正文不突出 | 区分背景与正文的职责；先减轻大面积工具表面，恢复主要文字分量，检查次文字的实际配对 |
| 每块内容都像独立卡片，轮廓过碎 | 合并本来属于连续内容的容器，减少重复边框和阴影，让分组间距承担关系 |
| 蓝色／暖色到处出现，重点不清楚 | 分别检查链接、主按钮、选中与状态；降低无功能的重复强调，保留有意义的内容色彩 |
| 字号都“合规”但阅读不舒服 | 分开调整工具与正文，比较中文行距、段落宽度、长标题及图标重量，而不只换字体 |
| 深色界面厚重或文字刺眼 | 比较相邻深色表面与文字亮度；减小大面积高亮灰块，保留当前操作与浮层的必要分离 |
| 桌面松散、手机拥挤 | 按活动调整信息密度和行宽；手机将次级工具放到合适入口，不缩小全部文字 |

这些是观察后的诊断方向，不预设每个界面都有这些问题，也不形成“必须低饱和”“禁止卡片”或固定强调色面积比例。可读性计算和美感判断分别说明：数值通过说明相应配对可读，整体是否优雅需要看真实画面与用户偏好。
