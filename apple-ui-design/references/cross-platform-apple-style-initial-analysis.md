# 苹果式精致与跨平台产品身份：初步方案分析

**状态：初步方案分析，供讨论与后续验证。**

**整理与来源核验日期：2026-11-12（北京时间）。**

本文保存关于 Codex、Claude Code、Craft 为何“有苹果气质，但在不同平台仍保持自身风格”的分析，区分官方已说明的事实、设计解释和待验证建议。用于风格分析、方案比较与后续验证选题；不将本轮判断升级为强制规范，不引入固定按钮数量、层级数量、配色或材质配额。

现行规则强度、平台适用范围及实现要求仍以 [SKILL.md](../SKILL.md) 和对应参考文件为准。本次仅补充研究材料，保留 Skill 3.1，不调整 Token，也不表示完成了三个产品的全面体验审计。

移动端的专项补充见[移动端初步方案](mobile-cross-platform-initial-plan.md)：进一步展开手机导航、触控与中文输入、原生 iOS／Android／移动 Web 的差异，以及切后台、离线和远程任务恢复；同样属于调研与候选方案，尚未进行实机验收。

桌面与手机的配色、字体、图标、圆角、阴影及材质组合，进一步见[视觉专项初步方案](desktop-mobile-visual-style-initial-plan.md)。该补充独立讨论视觉美感与两端样式关系，沿用现有 Token 合约并区分产品事实与候选设计。

## 1. 问题与核心判断

问题源于一种使用感受：Codex、Claude Code、Craft 的界面和流程让人联想到苹果设计，但又没有很强的苹果系统外观，在不同设备上仍然协调。

**本轮判断：精致程度与苹果系统辨识度是两个维度。** 清楚的排版、合理的注意力安排、连续反馈和细节完成度可以跨平台保留；产品自己的内容结构、品牌与任务逻辑决定其身份；系统操作则需要随平台和输入方式调整。

这一解释不意味着所有优秀界面都来自苹果，也不能由视觉相似推断三个产品共用组件库、技术框架或内部设计体系。Craft 对个别 Apple 交互的借鉴有官方说明；Codex 与 Claude Code 的“苹果感”主要是本轮对共同品质和工作流的设计解释。

Apple 的品牌设计课程明确讨论了独特品牌与熟悉平台模式的平衡；Google Material 3 也支持通过颜色、字体和形状表达品牌。这说明品牌身份与平台适配可以同时成立。[^apple-brand][^material-theme]

## 2. 四层分析模型

以下模型用于组织本轮讨论，是分析工具，不是 Apple 或三家厂商共同公布的官方架构。

| 层次 | 主要内容 | 跨平台处理方向 |
| --- | --- | --- |
| 视觉秩序 | 对齐、分组、文字层级、密度、状态辨识 | 保持关系与可读性，允许具体尺寸变化 |
| 产品品牌 | 配色角色、图标性格、排版、图像与文案语气 | 保持可识别的产品身份 |
| 任务与交互 | 主要对象、开始工作、编辑、审查、纠正与恢复 | 保留任务逻辑，按设备调整操作入口 |
| 系统惯例 | 返回、分享、键盘、菜单、窗口与系统控件 | 尊重目标平台及其真实能力 |

用户感受到的“苹果味”可能来自视觉秩序和完成度；强烈的系统辨识度则还与特定控件组合、导航、材质和窗口表现有关。两者可以分别调整，不宜用“更像 iOS”直接替代“更适合当前任务”。

## 3. 三款产品的证据与差异

### 3.1 Craft：具体借鉴经过产品化与跨平台打磨

**官方事实：** Craft 在 2024-09-05 的工程文章中说明，侧栏的 Fluid Segmented Control 受到 Apple 在 WWDC 2024 展示的 Mail 控件启发，设计师在 Figma 中重新设计，再实现适合自身侧栏的行为。文章还介绍了不同容器宽度、图标与文字组合，以及复选框在不同浏览器和 DPI 下的细节处理。[^craft-engineering]

**设计解释：** 借鉴可以发生在一个交互构思上，随后围绕产品对象、空间和输入条件重新实现。最终保留的是适合任务的机制与细节，产品自身的文档、内容卡片和编辑空间仍然能够被识别。

### 3.2 Codex：任务、执行与改动审查共享上下文

**官方事实：** Codex 的审查面板支持查看改动、提供逐行反馈，并围绕变更执行暂存或撤销等操作。[^codex-review]

**设计解释：** 用户提出的任务、正在发生的工作、产生的结果与后续纠正处于相互关联的上下文中。这种可追踪性与连续性能够形成稳定的工作台体验，不依赖某一种玻璃效果。

本分析没有据此证明 Codex 的设计团队在模仿苹果，也没有把某个桌面入口的布局推定为所有平台一致。

### 3.3 Claude Code：图形入口与终端需要分别讨论

**官方事实：** Claude Code 有终端、IDE、桌面与网页等入口。桌面 Code 标签把环境、项目、权限和模型安排在输入框附近，附件及扩展能力从“＋”进入；用户可停止任务，也可发送修正，让其在当前动作结束后调整下一步。[^claude-overview][^claude-desktop]

**设计解释：** 图形入口把开始工作所需的设置、继续指导以及结果查看放在相关位置，有助于减少上下文切换。终端版则主要依靠文字、命令、状态与反馈的组织体现秩序，不宜把圆角、玻璃等图形界面语言套到它身上。

### 3.4 产品气质的分析性归纳

| 产品 | 主要组织对象 | 本轮的气质归纳 |
| --- | --- | --- |
| Craft | 文档、内容块、页面关系 | 精细排版的创作与阅读空间 |
| Codex | 项目、任务会话、执行与改动 | 可追踪复杂工作的工作台 |
| Claude Code 图形入口 | 会话、项目、执行与结果 | 由对话带动、逐步展开的工作空间 |

这些称谓用于解释观感，不是品牌官方定位，也不代表三款产品的全部功能。

## 4. 视觉质感的形成

### 4.1 用关系安排注意力

正文、导航、操作和状态承担不同职责。可根据任务让正文容易阅读、导航能够定位、操作容易发现、状态足以解释变化。对齐、缩进、分组、留白和适当的渐进展示，均可建立这些关系。Apple Layout 将这些方法作为具体布局指导。[^apple-layout]

清爽并不等于信息少。代码审查、表格比较和编辑器可以保持较高密度；阅读界面也不必为了显得简洁而使用过大的留白。容器应表达对象、交互或有意义的分组，不能仅按装饰习惯给每一块信息加卡片。

### 4.2 排版是一组关系

关注标题与正文的大小和字重关系、行距、阅读宽度、图标与文字的视觉对齐、中文与拉丁字符混排、长标题换行，以及字号放大后的布局。Apple Typography 也强调可读性、信息层级和字体尺寸变化。[^apple-type]

Craft 在 2026-09-01 的更新中专门改进了 Web／Windows 的中日韩字体显示，包括粗体、斜体，并调整任务行间距。它可以作为“跨平台质感包含本地化排版工作”的事实例证。[^craft-cjk]

具体实现继续使用 [中文排版](chinese-typography.md) 和平台文本样式，不在本分析中另设一套固定字号。

### 4.3 区分安静的表面与模糊的信息

页面、侧栏和卡片之间可以只有细微差异，但重要文字、选中、焦点、禁用、警告与错误仍需容易区分。整体变淡并不自动改善层级，低饱和也不是品质的必要条件。

Material 3 用强调、表面和语义等颜色角色组织主题，并允许品牌化字体与形状。[^material-theme] 对本 Skill 而言，中性、鲜明、扁平、立体都可以成立；判断依据是任务、可读性和表达是否清楚。

### 4.4 一致的小决定累积成完成度

间距、图标视觉重量、圆角与容器比例、按钮状态变化、菜单焦点和内容展开位置，都可能影响连续使用时的感受。Craft 对复选框和分段控件的工程打磨是具体案例，不能直接证明所有产品都已完整处理这些状态。[^craft-engineering]

## 5. 工作流程与交互连续性

### 5.1 在合适阶段呈现复杂度

让用户开始任务时能够表达目标；在相关位置提供必要设置；需要精细控制时再展开更多能力。不要把全部技术选项一开始就作为前置决策，也不要把高频操作都藏入“更多”。

渐进展示应按真实任务使用：阅读者可能没有显著主操作，编辑器可能需要多个同等可用工具，比较界面可能需要同时展示信息。它不构成“每页只能有一个主按钮”的规则。

### 5.2 让操作与当前对象保持联系

选中文本后的操作、改动对应的反馈、任务产生的结果，都应让用户理解作用对象与影响范围。局部操作能否减少重新定位，是值得验证的方向；不是所有操作都必须原位完成。

### 5.3 保持状态可理解、结果可追溯

用四个问题审视相关流程：我在哪里、现在发生什么、结果在哪里、如何纠正。按操作能力考虑进度、待确认、成功、失败、取消和恢复。

Codex 的逐行审查与 Claude Code 的运行中修正，是上述分析的已说明功能案例。[^codex-review][^claude-desktop] 列表返回位置、滚动稳定性、完整错误恢复等其他行为，应在具体客户端验证，不能从截图或本分析推定通过。

### 5.4 动效解释变化

评估过渡是否帮助连接触发对象与结果、解释层级或状态改变。动效不应成为唯一反馈，也不能用柔和动画掩盖缓慢加载、跳动布局或任务状态不明确。采用什么运动参数仍由平台、任务与现有组件决定。

## 6. 跨平台的一致与适配

### 6.1 保持产品身份，调整具体动作

Craft 在 2026-05-19 的更新中给出以下实际差异：[^craft-input]

| 目标 | Mac／鼠标 | iOS／触屏 |
| --- | --- | --- |
| 显示看板顶部新增与选项 | 悬停出现 | 持续可见 |
| 操作条目 | 点击选中并原位编辑 | 点击进入子页 |
| 上下文操作 | 右键 | 长按 |

该证据覆盖的是原文所描述的设备与输入条件，不能由此声称 Android 具有完全相同的实现。它说明同一个对象与任务，可以有不同的可发现入口。

### 6.2 按可用空间改变展示方式

桌面上可同时展开列表、正文和详情；紧凑窗口可能需要分步进入。Google 自适应布局指南建议重排内容、设置合理最大宽度，并允许底部面板在大屏改为侧面板。[^android-layout]

因此，应保持对象名称、任务含义、状态和结果的可理解性，同时按窗口、输入方式与内容量调整布局。简单缩小桌面布局，或把内容无限拉宽，都不足以完成适配。

### 6.3 尊重宿主行为

Android 的系统返回、手势、安全区域、系统栏和键盘需要正确配合。Google 指南要求防止系统区域遮挡内容和操作，并考虑不同导航配置。[^android-system]

桌面窗口、快捷键、文件选择和辅助技术行为同样应使用所在环境的真实机制。外观上的统一不能代替这些适配；技术框架是否相同，也不能从视觉观感直接判断。实现时继续阅读 [Web 与跨平台](web.md) 及对应原生平台参考。

## 7. Liquid Glass 的作用与边界

**官方指导：** Apple Materials 将 Liquid Glass 主要用于浮在内容上方的导航和操作层，并要求节制使用，避免在内容层造成混乱。[^apple-materials]

**产品自述：** Craft 在 2025-09-15 的 Liquid Glass 更新中明确提出保留自身核心，只在能增加清晰度与专注度时使用玻璃。[^craft-glass]

**本轮解释：** 轻材质可以强化导航、操作与内容的空间关系；排版、层级和流程本身仍需要独立成立。增加模糊、圆角或阴影，不会自动修复主次不清、状态难辨或操作绕路。

具体使用仍应服从系统组件、实际背景和任务。主要阅读内容需要稳定可读，但这不等于要求所有正文一律纯色不透明。网页透明与模糊只是材质近似，不等于原生 Liquid Glass；Android、Windows 也不需要复刻所有苹果系统效果。

本轮曾用“系统组件主导、内容与品牌主导、玻璃装饰主导”三个概念方向说明视觉重心的差异。这只是解释工具，没有把概念界面作为真实产品截图、用户测试或性能证据。

## 8. 设计时的候选使用方式

以下方向仅用于后续比较与验证，不修改现有规则或 Token，也不针对任何具体产品。

### 8.1 候选定位

有自身品牌的跨平台产品：内容清晰、工具位置合理、操作连续；借鉴细节完成度，由具体产品的真实内容与工作方式决定最终形式。视觉安静可作为内容密集场景的候选方向，不扩展为所有页面的风格要求。

### 8.2 区域与对象职责

保留内容、任务、阅读等对象之间原有的关系。导航帮助定位，主区域承载当前活动，相关资料与操作围绕当前对象展开；界面整合不应制造重复的内容库或任务入口。

### 8.3 先比较关系，再选择材质

优先评估文字层级、间距、图标重量、选中状态、表面层级及颜色职责。白色、黑色、偏暖或偏冷的主题可以共享语义关系，但需要分别验证真实前景与背景组合。具体值沿用现有 [Token 合约](tokens.md)，本分析不增加新的数值标准。

### 8.4 在动作层完成设备适配

候选示例：桌面可以并列查看来源与详情，手机逐层进入并保持位置；桌面可展开更完整的执行信息，手机优先呈现当前进展、待处理事项与结果。是否适用，需要检查具体任务、内容密度和导航，不能仅凭本分析决定布局。

### 8.5 用材质强化已经存在的层级

可先尝试在导航、悬浮操作或临时工具中使用轻材质，再观察是否有助于识别与操作。长时间阅读区域以稳定可读为目标；关闭特效后结构仍清楚，可以作为一个检查方法，但不单独证明方案优劣。

## 9. 后续验证与使用边界

将以下问题作为与任务相关的候选验证项，不作为所有改动的强制完整审计：

- 真实中文长标题、混合文本与大字号下，层级和操作是否完整？
- 在目标 Android、iOS、Windows 客户端中，返回、键盘、焦点和触控是否自然？
- 导航与结果之间的上下文、阅读位置及任务状态能否正确保留？
- 高频操作是否容易发现，次要功能是否可以在需要时找到？
- 关闭透明或减少动态后，关键信息和操作是否仍然成立？
- 材质在实际背景及目标设备上是否改善辨识度，是否引入可读性或性能问题？

尚未验证的内容包括真实使用任务下的效果、不同客户端的完整行为、用户偏好比较以及性能与无障碍结果。当前分析没有完成这些实测，不应写成“已优化”“已兼容”或“已验收”。

后续如需将某条建议纳入正式规则，应附具体问题、适用场景、方案比较和验证结果，再更新对应参考文件。避免把“更像苹果”“更多玻璃”“更浅的灰色”单独作为验收标准。
